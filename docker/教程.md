# 把 typespeed 跑进 k8s：健康检查、优雅停机与部署清单

> 本章教程配套 typespeed 2.6.x 的「k8s 原生友好」能力——框架内建健康检查与优雅停机 + 官方 Docker/k8s 部署清单。
> 阅读前提：会用 typespeed 起一个服务（`@app` + `@component` + `@getMapping` 那套）。
> 本文按「**为什么 → 怎么用 → 原理 → 怎么扩展**」四段展开。
>
> 配套文件：`docker/Dockerfile`、`docker/docker-compose.yml`、`docker/k8s/`、`docker/helm/`。

---

## 一、为什么：让框架「k8s 原生友好」

typespeed 的定位是**单体 Web 框架**（对应 SpringBoot）。单体框架要跑在云原生环境里，绕不开三件事：

1. **探针**：k8s 靠 `readinessProbe` / `livenessProbe` 判断服务「能不能接流量」和「进程死没死」。框架如果没有标准化的健康检查端点，每个应用就得自己写，写法还五花八门。
2. **优雅停机**：k8s 滚动更新/缩容时先发 `SIGTERM`，给服务一个「排空在途请求」的窗口，超时再 `SIGKILL`。如果服务收到 `SIGTERM` 直接死，在途请求就丢了。
3. **部署清单**：每个应用都手写 Dockerfile / k8s yaml，重复且易错。官方提供模板，复制即用。

所以 2.6.x 的目标是：**这三件事框架内建 + 官方模板**，应用零成本变成「k8s 原生友好」。

具体实现为：

| 能力 | 版本 | 说明 |
|---|---|---|
| 健康检查 | 2.6.2 | 内建 `GET /health`（liveness）+ `GET /ready`（readiness） |
| 优雅停机 | 2.6.3 | `SIGTERM`/`SIGINT` → 优雅关闭 → exit 0 |
| 部署清单 | 2.6.4 | 官方 Dockerfile / compose / k8s / Helm 模板 |

## 二、怎么用：四步把服务跑进 k8s

### 2.1 健康检查：开箱即用

typespeed 2.6.2 起，服务启动后**自动**多了两个端点，什么都不用配：

```bash
curl http://localhost:8080/health   # → {"status":"up"}     (200)
curl http://localhost:8080/ready    # → {"status":"ready"}   (200)
```

- **`/health`（liveness）**：进程活着就返回 200，k8s 用它判断「要不要重启」。
- **`/ready`（readiness）**：返回 200 表示「可以接流量」，k8s 用它判断「要不要把流量分给这个 Pod」。

路径可配置（默认 `/health`、`/ready`），在 `config.json` 里加：

```json
{
  "health": {
    "liveness": "/health",
    "readiness": "/ready"
  }
}
```

### 2.2 优雅停机：收到信号就优雅退出

2.6.3 起，框架在服务启动时自动注册 `SIGTERM` / `SIGINT` 处理：收到信号 → 关闭 HTTP 服务（排空在途连接）→ 退出码 0，30 秒超时强制退出。所以 k8s 滚动更新时，你的服务会「体面地」退出，不丢在途请求。

验证方式（`npm run test:shutdown`）：

```bash
./node_modules/.bin/ts-node --transpile-only app/src/main.ts &
kill -TERM $!        # 日志出现 "received SIGTERM ... server closed"，退出码 0
```

### 2.3 Docker 镜像：多阶段构建

官方 `docker/Dockerfile` 是**多阶段构建**——构建阶段编译 TS，运行阶段只留产物 + 生产依赖，镜像更小：

```dockerfile
# 构建阶段：编译 TypeScript
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# 运行阶段：只装生产依赖 + 复制产物，非 root 运行
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm install --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://127.0.0.1:8080/health || exit 1
CMD ["node", "dist/main.js"]
```

关键点：**构建/运行分离**（镜像小）、**非 root 运行**（安全）、**内置 HEALTHCHECK**（对应 `/health`）。

构建镜像：

```bash
docker build -t typespeed-app:latest .
```

### 2.4 k8s 部署 + Helm

官方 `docker/k8s/` 提供 `deployment.yaml` + `service.yaml` + `ingress.yaml`，其中 Deployment 已经接好了探针：

```yaml
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /health, port: 8080 }
  initialDelaySeconds: 15
  periodSeconds: 10
```

直接部署：

```bash
kubectl apply -f docker/k8s/
```

或用 Helm（`docker/helm/`）：

```bash
helm install my-app docker/helm --set image.repository=typespeed-app
```

本地一键起整套（app + MySQL + Redis + RabbitMQ）：

```bash
docker compose -f docker/docker-compose.yml up -d
```

## 三、原理：探针与停机背后的机制

### 3.1 健康检查 = 工厂模式

`/ready` 不是写死的——它读一个 **`HealthFactory`**（工厂），应用可覆盖就绪逻辑：

```ts
// 框架内建
export default abstract class HealthFactory {
    abstract ready(): boolean;
}

// 默认实现：恒就绪
export default class HealthDefault extends HealthFactory {
    @bean
    createHealth(): HealthFactory { return new HealthDefault(); }
    ready(): boolean { return true; }
}
```

`ExpressServer` 在 `setDefaultMiddleware()` 里注册两个路由，`/ready` 读 `getBean(HealthFactory).ready()`，`false` 返回 503（k8s 就会停止分流）。这套「工厂 + 默认实现 + 可覆盖」的模式，和 `LogFactory` / `CacheFactory` 一脉相承。

### 3.2 优雅停机 = 存储 httpServer + 信号处理

`ExpressServer.start()` 之前直接 `return this.app.listen(port)`，拿到 http.Server 就丢了。2.6.3 把它存到 `this.httpServer`，并注册信号处理：

```ts
public start(port: number): any {
    // ...
    this.httpServer = server;      // 存起来
    this.registerGracefulShutdown();
    return server;
}

private registerGracefulShutdown() {
    const shutdown = (signal: string) => {
        // 30 秒超时强制退出
        const forceExit = setTimeout(() => process.exit(1), 30000);
        forceExit.unref();
        Redis.close().catch(() => {});          // 关 Redis 连接
        this.httpServer.close(() => {            // 排空在途请求后关闭
            clearTimeout(forceExit);
            process.exit(0);
        });
    };
    process.on("SIGTERM", () => shutdown("SIGTERM"));
    process.on("SIGINT", () => shutdown("SIGINT"));
}
```

关键语义：**`httpServer.close()` 会等已建立的连接处理完再真正关闭**——这正是 k8s 想要的「排空」。而 30 秒超时保证「卡死的连接不会拖住退出」。

### 3.3 多阶段构建 = 构建/运行分离

多阶段 Dockerfile 的精髓：构建阶段有完整的 devDeps（typescript 等）编译出 `dist/`，运行阶段只装生产依赖（typespeed、express）+ 复制 `dist/`。这样最终镜像里没有 TypeScript 编译器、没有源码，体积大幅缩小，攻击面也小。

## 四、怎么扩展

### 4.1 自定义就绪检查（接数据库/Redis）

`/ready` 默认恒 true 太「乐观」——你的服务可能依赖 MySQL，MySQL 挂了服务其实「没就绪」。继承 `HealthFactory` 覆盖就绪逻辑：

```ts
import { HealthFactory, bean } from "typespeed";

export default class MyHealth extends HealthFactory {
    @bean
    createHealth(): HealthFactory { return new MyHealth(); }

    ready(): boolean {
        // 检查数据库/Redis 连通性，返回是否就绪
        return this.dbOk() && this.redisOk();
    }
    // ...
}
```

这样 `/ready` 就会真实反映「依赖是否就绪」，k8s 只在依赖就绪时才分流。

### 4.2 自定义探针路径

`config.json` 里改 `health.liveness` / `health.readiness`，就能把探针挂到自定义路径（避免和业务路由冲突）。

### 4.3 扩展部署清单

`docker/k8s/` 和 `docker/helm/` 是**最小可用模板**——按需加 `configmap`、`secret`、`serviceAccount`、`hpa`（水平自动扩缩）。k8s 清单的 `resources.requests/limits` 已经留了位置，按你的服务负载调。

## 小结

typespeed 2.6.x 让「把服务跑进 k8s」变成三步：

1. 服务不用改——`/health`、`/ready` 自动有，`SIGTERM` 自动优雅停机；
2. 复制官方 `docker/` 清单，改个镜像名/端口就能部署；
3. 有特殊依赖，就继承 `HealthFactory` 自定义就绪检查。

这是 typespeed 从「能写 Web 服务」到「能上生产集群」的一步。呼应「公司 platform/k8s 练的部署/探针/优雅停机经验，总结成框架能力」。
